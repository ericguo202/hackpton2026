# InterviewPie: AI Interview Coach

MVP: Voice-in → transcript → LLM scoring + follow-up → ElevenLabs voice-out → metrics + incidents persisted.

## Question-type taxonomy (expansion in progress — next major move)

Today every opening question is one type: **Experience (STAR)** — "tell me about a time…". That's repetitive for our target users (students, later college career centers): career centers (Princeton, Columbia, UC Davis, UConn) prep students on behavioral, situational, AND traditional/self-presentation questions, and situational questions are specifically recommended for candidates with limited work history (UNC; U.S. OPM ranks them highest-value for internship/entry users). The four types:

- **Experience (STAR)** — the current behavior. All existing question-generation machinery below (STAR field prompts, `STAR_FIELD_EXAMPLES`, `sample_question_themes`, STAR evaluator rubrics, STAR follow-up probe angles) is scoped to this type — the STAR-specific modules/functions are explicitly named (`_star_opening_prompts.py`, `_star_evaluator_rubric.py`, `build_star_opening_prompt`, etc.). Each turn is labeled by its type on `interview_turns.question_category` (the `QuestionCategory` enum; default `experience_star`).
- **Self-Assessment & Growth** — strengths/weaknesses, biggest failure, feedback received. NOT built yet.
- **Motivation & Fit** — tell me about yourself, why this role, why this company, goals and preferred environment. **BUILT (prompt stack + dispatch) — see the "Motivation & Fit" bullet below.**
- **Situational (Hypothetical)** — hypothetical scenarios; highest value for internship/entry users. **BUILT (prompt stack + dispatch + routed live) — see the "Situational" bullet below.**

When touching opening-question / rubric / follow-up code, assume it is parameterized by question type — don't deepen the STAR-only assumption.

**Generic score plumbing (built with M&F).** Different question types score DIFFERENT content dimensions (STAR: structure/problem_solving/impact/initiative/depth; M&F: structure/relevance/company_insight/career_narrative/conviction; Situational: structure/reasoning/principles/practicality/evidence). So the five content score slots are GENERIC end-to-end — `interview_turns.dimension_1..5_score`, `session_metrics.avg_dimension_1..5`, wire `ScoresOut.dimension_1..5` / `DimensionAverages.dimension_1..5` (migration `0026_generic_dimensions`, renamed from the STAR-named columns). Position 1 is Structure for every type; `delivery` is the shared 6th slot. The evaluator LLM still emits SEMANTIC keys per type; `evaluate_turn` remaps them onto `dimension_N` via `_score_dimensions.evaluator_json_keys`. The human LABEL per position is resolved from the turn's `question_category`: backend `app/services/_score_dimensions.CONTENT_DIMENSION_LABELS` (used by the Ask-Tutor context), frontend `lib/scoreDimensions.ts:scoreDimensionsFor(category)` (per-turn views label by `turn.question_category`; **per-session aggregate** views — SessionDetail + Practice Results overview tiles — label by the session's category off `turns[0].question_category` since a session is single-category; **cross-session** views — history trend, radar, `/me/stats` — and SavedQuestionDetail (STAR openings only) keep the STAR `SCORE_DIMENSIONS` set). **Routing is LIVE (single-category per session).** The Setup picker sends `SessionCreateIn.question_category` — allowlisted to the built types `{experience_star, motivation_fit, situational}` via `schemas/session.BUILT_QUESTION_CATEGORIES` (422 on an unbuilt value; extend the set as new types ship). A custom-question session is forced back to `experience_star` (the verbatim user text isn't a generated M&F/situational opening). The chosen category is stamped on turn 1 in `_persist_session_and_turn`, and `submit_turn` propagates it with `next_question_category = current_turn.question_category` so every routed opening/follow-up inherits it (no separate routing decision). Surfaced as `first_question_category` (create) / `next_question_category` (submit). Setup UI: `QuestionTypeField.tsx` next to the length control; frontend picker source `types/session.SELECTABLE_QUESTION_CATEGORIES`.

## What the MVP ships

- **Personalization from a resume.** Onboarding ingests PDF resume + short bio → `resume_text`, `target_role`, `industry`, `experience_level`. Every downstream prompt conditioned on this profile.

- **Industry & role autocomplete (required-selection combobox).** `/api/v1/validation/industries?q=` and `/api/v1/validation/roles?q=&industry=` → `SuggestionsOut { suggestions: str[≤5], flagged, message }`. Three-stage pipeline (order is load-bearing — moderation MUST precede LLM): (1) deterministic `_looks_like_junk` reject → empty, no network; (2) OpenAI `check_moderation` → empty + `flagged=True` on block; moderation outage raises `ModerationUnavailableError` → empty (unmoderated input never reaches LLM); (3) LLM `google/gemini-2.5-flash-lite` → `deepseek/deepseek-v4-flash` (no reasoning) fallback, JSON `{"suggestions":[...]}`, ≤5 unique Title-Case strings. Fails soft → empty. Suggestions are **semantic not literal completions**. Role conditioned on chosen industry (empty → industry-agnostic). UI: `SuggestionCombobox.tsx` (ARIA listbox, 350ms debounce via `useDebouncedValue`) wrapped by `IndustryAutocompleteField`/`RoleAutocompleteField`. **Required selection** — free-typed text never advances, editing re-arms; gate is client-side only. Validation `category` no longer returned (recomputed at session time by `company_research`).

- **Voice dictation for the bio field (browser-native Web Speech API).** Deliberately **NOT** ElevenLabs STT (wrong shape for inline textbox). Three pieces:
  - `useSpeechRecognition.ts` — `continuous=true`, `interimResults=true`; `onend` auto-restart gated by `wantListeningRef`; `not-allowed`/`service-not-allowed` → error + stop; `no-speech`/`aborted` ignored.
  - `SpeechToTextButton.tsx` — **renders `null` when `!supported`** (Firefox). Does NOT own the bio value.
  - `joinSpoken.ts` — `joinSpoken(prev, chunk)` merges finalized chunks (single space, clamp to `MAX_BIO_LENGTH = 2000`). **Interim text never committed.** Own module for `react-refresh/only-export-components`.

- **Field-tailored opening question AND evaluator rubric.** 15 field buckets: Tech/Product/Design, Data/AI/ML, Cybersecurity, Finance, Consulting, Legal, Government, Healthcare, Sales/Marketing, Ops/Supply Chain, Retail/Hospitality, Nonprofit, Education, Non-Software Engineering, Startups. Classified by job title (primary), company (secondary). The `FieldCategory` taxonomy is the **shared domain axis** — it lives in `_field_categories.py` (never STAR-specific; reused by all four question types). Category drives (1) opening-question prompt (`_star_opening_prompts.py`, STAR-scoped today) and (2) evaluator rubric (`_star_evaluator_rubric.py`, STAR-scoped today). Source-of-truth markdown: `backend/prompts/star_opening_question_prompts.md`, `star_evaluator_prompts.md` — **keep Python and markdown in sync**. **STAR seam:** the opening/evaluator/follow-up prompt CONTENT that assumes "tell me about a time…" is now explicitly STAR-named (`build_star_opening_prompt`, `STAR_FIELD_EXAMPLES`/`STAR_FIELD_THEMES`, `build_star_system_instruction`, `_STAR_PROBE_ANGLES`/`_STAR_FOLLOWUP_EXAMPLES`); the four-type expansion adds sibling modules per the taxonomy above.

- **Experience-level tailoring (second axis).** `ExperienceLevel`: internship / entry / mid / senior / staff / executive. **15×6 matrix** via `experience_question_block(category, level)` / `experience_evaluator_block(category, level)`.
  - **Opening question** (`build_star_opening_prompt`): experience block **leads as `PRIMARY DRIVER`**, `STAR_FIELD_THEMES` demoted to background. Shared `style_cues` keep the legacy `None` path byte-identical.
  - **Evaluator** (`build_star_system_instruction`): level paragraph appended, keyed on same resolved `key` as the rubric fallback.
  - `experience_level is None` (legacy) → byte-identical to category-only. Non-`ExperienceLevel` → `""` (fails soft).
  - **Source of truth:** `backend/prompts/experience_prompts.md`; `_experience_prompts.py` is **generated** via `python scripts/gen_experience_prompts.py` — don't hand-edit the `.py`. Import-time guard fails loud if any of the 90 cells is missing.

- **Motivation & Fit question type (2nd of 4 — BUILT; not routed live).** Full sibling prompt stack to STAR, dispatched by `QuestionCategory`. Scores 5 DIFFERENT content dims (Structure / Relevance / Company Insight / Career Narrative / Conviction) onto the generic `dimension_1..5` slots (see the taxonomy section's "Generic score plumbing"). Reachable when `next_question_category` flips to `motivation_fit`; every generator already threads `question_category`.
  - **Archetype axis (M&F-only, `_archetypes.py`).** Research shows M&F questions barely change by industry — what changes is which dimension is decisive + the disqualifying answers. So the 15 fields collapse to **5 archetypes** (`ARCHETYPE_BY_FIELD`, fail-loud complete): A commitment-screened (finance/consulting/legal), B mission-screened (gov/health/nonprofit/edu), C values-codified (tech/data/cyber/eng), D persuasion-demonstrated (sales), E environment-fit (ops/retail/startups). Each `ArchetypeProfile` carries a question-guidance fragment, an evaluator **weighting note** (which dims decisive), and **Conviction taboos** (documented insta-fails: exit-opps/comp in A, mercenary in B, "want stability" in E). `archetype_for(category)` resolves it (default field's archetype on unknown). **This axis does NOT carry over to STAR.**
  - **Opening** (`_motivation_fit_opening_prompts.build_motivation_fit_opening_prompt`, field-INDEPENDENT pool). `opening_question.generate_opening_question(question_category=...)` dispatches; the M&F branch (`_build_mf_user_prompt`) is **company-CENTRIC** (always surfaces company facts — the STAR "standard style" that forbids naming the company is wrong for "why this company"), no style rotation. SoT `backend/prompts/motivation_fit_opening_question_prompts.md`.
  - **Evaluator** (`_motivation_fit_evaluator_rubric.build_motivation_fit_system_instruction`, field-INDEPENDENT base + archetype/level tail). Emits M&F semantic keys → remapped to `dimension_N`. Appends the archetype weighting + Conviction taboos + a **level-scaled Company Insight anchor** (entry = effort/specificity; mid/senior = self→role mapping; staff/exec = strategic-situation awareness). `evaluate_turn` dispatches STAR vs M&F and **skips `_calibrate_content_scores` for M&F** (STAR evidence caps — metrics, "I"-ownership — unfairly depress a good "why this company" answer). `issue_type` enum gained M&F members (`generic_pitch`, `no_company_specifics`, `incoherent_narrative`, `mercenary_framing` — additive; STAR unaffected). SoT `backend/prompts/motivation_fit_evaluator_prompts.md`.
  - **Follow-up** (`followup.py`): `_followup_prompts(question_category)` selects the M&F system/transition/decision prompts + probe/example pools (motivation-depth / specificity / coherence probes, Archetype-A "why not X" stress-tests — NOT story-result probes). Threaded through `generate_followup`, `generate_followup_transition`, `should_continue_followup`, and `_build_user_prompt`/`_render_variety_block`.
  - **Experience matrix (M&F).** **archetype × level (5×6 = 30 cells)**, NOT field×level — M&F questions are field-independent. `_motivation_fit_experience_prompts.py` is **generated** via `python scripts/gen_mf_experience_prompts.py` from `motivation_fit_experience_prompts.md` (don't hand-edit); import-time guard fails loud on a missing cell. Helpers `mf_experience_question_block(archetype, level)` / `mf_experience_evaluator_block(...)`.

- **Situational (Hypothetical) question type (3rd of 4 — BUILT + routed live).** Full sibling prompt stack to STAR, dispatched by `QuestionCategory.situational`. Scores 5 DIFFERENT content dims (Structure / Reasoning / Principles / Practicality / Evidence) onto the generic `dimension_1..5` slots. Unlike M&F, situational is **field-dependent (15×1), NOT archetype-based** — there is NO archetype axis and NO archetype×level matrix. The level axis drives the evaluator (the "escalation flip"); question generation is field-DRIVEN, with the level threaded only as a **light fit guard** (not a PRIMARY-driver matrix like STAR/M&F) so a scenario's scope/authority matches the candidate.
  - **Dilemma requirement (load-bearing).** The single validity-bearing rule from the situational-interview literature: every opening question must contain a genuine DILEMMA — the scenario forces a choice between two or more **mutually exclusive** courses of action, each with a real cost. Encoded in `_situational_opening_prompts._SITUATIONAL_OPENING_FORM_CLAUSE`. A weak "what would you do if X?" with an obvious answer is not acceptable.
  - **Opening** (`_situational_opening_prompts.build_situational_opening_prompt(category, experience_level, rng)`, field-keyed). `SITUATIONAL_FIELD_SCENARIOS` (15×5 scenario-genre themes) + `SITUATIONAL_FIELD_EXAMPLES` (15 pools, 2-of-N sampled), mirroring `STAR_FIELD_*`. Experience level is threaded as a **light fit note** (`_SITUATIONAL_LEVEL_NOTE_TEMPLATE`, empty-omission when None) — keeps the scenario's scope/authority realistic for the level (e.g. no "manage a subordinate" dilemma for an intern), NOT a PRIMARY-driver matrix like STAR/M&F. The dispatch branch in `opening_question.generate_opening_question` passes `user.experience_level` and uses `_build_situational_user_prompt` (scenario-centric: surfaces the company's principles/values via `_company_digest` to ground the dilemma in a real stakeholder-value tension). SoT `backend/prompts/situational_opening_question_prompts.md`.
  - **Evaluator** (`_situational_evaluator_rubric.build_situational_system_instruction`, STAR-style base + `{industry_guidance}` tail). Emits situational semantic keys → remapped to `dimension_N`. Base rubric encodes the **scoring-guide-not-key** rule (accept MULTIPLE valid courses of action, grade the reasoning) + 2/5/9 benchmark anchors. `SITUATIONAL_INDUSTRY_GUIDANCE` = 15 per-field eval emphases (fail-loud complete). `_ESCALATION_FLIP_LEVEL_ANCHOR` (6-entry, hand-written like M&F's company-insight anchor) appended per level — at internship/entry, knowing when to escalate is a HIGH anchor for Reasoning; at staff/exec, deferring upward is a LOW anchor. `evaluate_turn` **skips `_calibrate_content_scores`** for situational (it's STAR-only; a hypothetical legitimately lacks metrics/"I"-ownership). `issue_type` enum gained situational members (`no_decision`, `unrealistic_plan`, `invented_facts`, `no_experience_tie` — additive). SoT `backend/prompts/situational_evaluator_prompts.md`.
  - **Follow-up** (`followup.py`): `_followup_prompts(situational)` selects the situational system/transition/decision prompts + probe/example pools — twist-focused (stress the SPECIFIC choice the candidate made, e.g. "you chose to escalate — your manager is unreachable for 48 hours; now what?"), probe trade-offs / second-order effects / the principle behind the call — NOT story-result probes. M&F-style twist pools only (no scripted-probe threading).
  - **Research (situational-specific — unlike M&F).** `company_research.research_company(question_category=...)` selects a situational variant (Serper + JD paths) that surfaces accurate company **principles / stakeholder values** (`values`, cap raised to 4 — feeds the Principles dimension + the dilemma grounding) and **situational-shaped `sample_question_themes`** (scenario/dilemma themes, not STAR "tell me about a time"), plus a values/judgment-oriented Serper role query. STAR/M&F keep the byte-identical behavioral instruction. `sessions.py` resolves the effective category BEFORE the research call so the variant is selected. SoT for the variant lives inline in `company_research.py` (kept in lock-step with the behavioral blocks).

- **Research-inspired, per-session-varied opening question.**
  - `STAR_FIELD_EXAMPLES`: 8–12 per category (varies), **2 randomly sampled per call** — breaks "fixed attractor" effect.
  - Two parallel Serper queries via `asyncio.gather`: `{company}` + `{company} {level_label} {job_title} behavioral interview culture`. Generic "interview questions" phrasing dropped — that corpus is LeetCode/system-design heavy and pulled `role_signals` technical.
  - `role_signals` = cultural/soft-skill traits (NO technical proficiencies); `sample_question_themes` = behavioral theme labels (NO technical themes, NO verbatim questions). Both default `[]`.
  - **Empty-omission pattern (load-bearing):** `_company_digest` surfaces these **only when non-empty** — reused by `followup.py` and `SessionDetail.tsx` Overview.
  - **Recent-questions avoid-list:** `users.recent_opening_questions` (JSONB, `'[]'` default, migration `0008_recent_opening_qs`) caches 3 most recent questions, newest-first. Injected into user prompt as avoid-list (empty-omission). Rolled via `([opening_q] + old)[:3]`, **reassigned not mutated** (SQLAlchemy dirty-tracking). **Reset to `[]`** in `onboarding.py` whenever `target_role`/`industry`/`experience_level` changes. Not in `UserOut`.

- **Optional pasted job description (per-session).** Setup's Advanced panel takes an optional posting (`SessionCreateIn.job_description`, ≤6000 chars, mirrored client-side `MAX_JOB_DESCRIPTION_CHARS` in `AdvancedPanel.tsx`). When present it becomes the **sole research source** — `research_company(..., job_description=...)` **skips both Serper queries** and derives the brief from the posting via `_research_from_job_description` + `_JD_SYSTEM_INSTRUCTION` (**seven-key** contract; same category list/anti-hallucination posture as the Serper path, existence-validation dropped since the match-check already vetted the company; kept a separate static block for its own Gemini implicit-cache prefix). Brief cleanup is the shared `_normalize_brief_payload` (category fallback + list caps) used by both paths. `job_description.py` owns the two setup-time pieces, **all in `POST /sessions` before any billed call:**
  - **Persisted role summary (`jd_summary`, fixes the "solo role, group question" bug).** The raw ≤6000-char JD is **never persisted** (token sink), so the JD research path additionally emits `CompanyBrief.jd_summary` — **1–5 short bullets of concrete ROLE facts** (solo vs. collaborative, scope/ownership, day-to-day duties, reporting line, key expectations; **excludes** company marketing, pay/benefits, tech-stack lists). Distinct from `headlines`/`role_signals` (factual grounding, not values). **Serper path never emits it → defaults `[]`.** It rides inside the persisted `company_summary` JSON (no migration; auto-survives re-practice, which copies that blob verbatim) and is threaded — **empty-omission gated** — into all three generation calls: opening question (`_jd_summary_block` in the user prompt — in the **company-flavored** style branch it additionally nudges the model to draw co-equal inspiration for the question's topic from the JD bullets; the standard branch keeps grounding-only framing), follow-up (`generate_followup(jd_summary=...)` → `_render_context_block`), and evaluator (`evaluate_turn(jd_summary=...)` → `_build_prompt`, **calibration-only context — NOT a scoring dimension/rubric change**). In `submit_turn`, `brief_out.jd_summary` threads alongside `category` through `_followup_and_tts` / `_run_background_eval` / `_spawn_finalize` → `_run_background_finalize` (and the lazy reaper). Backend-only — surfaced on the wire in `CompanyBriefOut` but no UI.
  - **Gibberish gate** (`looks_like_gibberish`, free/local) → `422`. Conservative hard block — rejects only empty/no-letters, symbol-soup (alphabetic ratio `<0.45` over ≥40 chars), or low-entropy keysmash (≥24 letters, ≤4 distinct). Real postings always pass. **Can't reuse `_looks_like_junk`** (its >120-char reject kills every real JD).
  - **Profile↔JD match-check** (`check_job_description_match`, `openai/gpt-oss-120b:free`, low reasoning → `deepseek/deepseek-v4-flash` no-reasoning fallback) → `409 {code: "job_description_mismatch", message}` on a clear mismatch (different professional domain, or company/posting obviously fake/joke). **Fails open** — any SDK/parse error returns a match so an LLM outage never blocks a real session (this is a UX guardrail, NOT a security boundary; injection + moderation are the hard blocks and run on the JD too). Skipped when `acknowledge_mismatch=true`.
  - **Acknowledge override:** frontend re-submits with `acknowledge_mismatch=true` (the `MismatchConfirmDialog` "Continue anyway" path); server skips the match-check and logs `job_description_mismatch_ack` (warning, `log_jd_mismatch_acknowledged`) for after-the-fact abuse visibility — the daily-session cap bounds spend.

- **Field-tailored, confusion-aware follow-up question.** `followup.py` (DeepSeek v4 Flash, no reasoning).
  - `generate_followup` accepts `category`, `role_signals`, `sample_question_themes`, `experience_level` (all default `None` — legacy `brief_out is None` sessions work). Experience level is one calibration line, not a matrix lookup.
  - **Variety machinery (fixes "too similar / too forced" follow-ups).** Two axes, mirroring the opening generator's anti-"fixed-attractor" design: **(1) Anti-repetition** — `generate_followup(already_asked=..., block_history=...)` feeds a **within-session avoid-list** (`_session_asked_questions` — every question posed this interview, openings + follow-ups; `_render_avoid_block`, mirrors `opening_question._recent_questions_block`) plus the **current block's prior Q/As** (`_current_block_history(...)[:-1]` → `_render_block_history`) so a 2nd follow-up in a block probes a genuine gap instead of echoing the 1st. Cross-session recents stay openings-only (follow-ups are answer-contextual). **(2) De-templating** — `_render_variety_block` samples **2-of-N** from `_STAR_PROBE_ANGLES` (~10 probe *dimensions*) + `_STAR_FOLLOWUP_EXAMPLES` (~12 varied-shape exemplars) per call (`_sample`, injectable `rng` for tests / `None` in prod, mirrors `_star_opening_prompts` 2-of-N sampling); the old **3 static "Good examples" are removed** from `_SYSTEM_PROMPT` and the hard "reference something concrete they said" rule is **softened** ("you MAY, but vary your entry; do NOT open every follow-up with 'You mentioned…'"). Sampled content lives in the **user** message so `_SYSTEM_PROMPT + _SECURITY_CLAUSE` stays a stable cache prefix. `temperature` **0.4 → 0.7** (matches opening). The anti-repetition params (`already_asked`/`block_history`) are **empty-omission** and default `None` (callers that omit them still work); the **variety block renders on every call by design** — 2-turn / single-follow-up sessions get de-templated too (that's the fix, so follow-up prompts are intentionally no longer static). `should_continue_followup` cadence unchanged (fix variety, not pacing). **No markdown source-of-truth** for follow-ups (kept in-code, unlike opening/evaluator).
  - **Confused-candidate rule:** off-topic/nonsensical/single-word → gently redirect concretely; do NOT echo back or pretend it was substantive.
  - Output through `_sanitize_followup` (strips wrap-quotes, `Question:`/`Q:`/`Follow-up:` labels, asterisks). **A "drop preamble" trimmer was DELIBERATELY NOT added** (false-positives on legit framings); meta-reasoning suppression lives in the prompt.
  - **Spoken transition bridge (audio-only, `generate_followup_transition`).** The live `submit_turn` path calls `generate_followup_transition(...)` (via `_followup_and_tts`), **not** the plain-text `generate_followup` — that function is now a **dormant fallback** with no live caller — retained only as a plain-text alternative (it carries its own mirror of the injection backstop). End-to-end tests target `generate_followup_transition`; the two share `_build_user_prompt` / `_sanitize_followup`, so the shared helpers stay covered. The transition generator returns a `GeneratedQuestion(question, spoken_bridge)` from a **JSON** system prompt (`_TRANSITION_SYSTEM_PROMPT + _SECURITY_CLAUSE`, `response_format=json_object`, same DeepSeek v4 Flash / v3.2, no-reasoning, temp 0.7, same `_build_user_prompt` as `generate_followup`). The **`question` is the only durable/visible artifact** — persisted to `turn.question_text`, returned on the wire, and the sole return value of `_followup_and_tts` (the bridge never enters history). The **`spoken_bridge` is TTS-only** — `_tts_text(generated)` prepends it (`"{bridge} {question}"`) to the string handed to `synthesize_speech`, so the interviewer *sounds* attentive without polluting the transcript/DB.
    - **Bridge is optional + heavily gated to degrade to `None`.** `_sanitize_bridge` drops it unless it's a single non-`?` sentence of 4–14 words that clears the `_BAD_BRIDGE_RE` blocklist (no "thanks/okay/got it/let's switch", no "the user…/I'll…" meta-reasoning, no praise/thanks); a valid bridge missing terminal punctuation gets a `.` appended. The visible `question` must clear `_valid_visible_question` (≥15 chars, exactly one sentence, ends in `?` or an imperative like "Tell me about…") or the **whole payload falls back** to the generic `_FALLBACK` question (no bridge). Injection in the transcript → same `_FALLBACK`, no LLM call, logs `followup.transcript`.
    - **Logging:** `generate_followup_transition` emits an `INFO` line showing the actual `spoken_bridge` (or `(none)`), the visible `question`, and the composed TTS text — inspect the console per non-final turn. `logger.debug` carries the raw JSON.

- **Variable-length interview session with auto-submit.** Per-session `num_turns` (2–8, default 2, `interview_sessions.num_turns`; migration `0023_session_num_turns`, DB check `num_turns BETWEEN 2 AND 8`). Chosen via the Setup Advanced-panel slider (`MIN/MAX_SESSION_TURNS` in `AdvancedPanel.tsx`, mirrored `SessionCreateIn.num_turns` `ge=2,le=8`), echoed on `SessionCreateOut`/`SessionDetailOut`. `num_turns=2` is byte-identical to the legacy 1-opening + 1-follow-up flow. Auto-Submit toggle stored in browser `localStorage` (`auto_submit_enabled`) — client-side preference only, not persisted to the backend. Both lock with `disabled={submitting}`.
  - **Story-block interviews (routing lives in `submit_turn`).** A longer interview is broken into **story blocks** — a fresh **opening** question + **1–2 follow-ups** — instead of one story chained to `num_turns-1` follow-ups (which degenerates). After answering a turn, the next turn's type is routed from the just-answered turn via `_block_route(fu_streak, has_brief)`: streak 0 (answered an opening) → follow-up #1 always; streak 1 (answered follow-up #1) → **model decides** via `followup.should_continue_followup(...)` (deepseek-v4-flash, no reasoning, tiny JSON `{"more_followup":bool}`, **fails soft → pivot to a new opening**); streak ≥ 2 → **forced pivot**. A missing/legacy brief (`_service_brief_from_out` → None) collapses routing to a single follow-up (keeps legacy rows byte-identical). Mid-session openings reuse `generate_opening_question` (research reused from `session.company_summary` — no Serper; `_opening_and_tts`) with `is_followup=False`/`parent_turn_id=None`; follow-ups keep `is_followup=True`/`parent_turn_id=<block opening>` (`_block_opening_id`). `_insert_next_turn` handles both. `num_turns=2` never reaches the opening branch. Odd `num_turns` can end on an opening with no follow-up (accepted). **Pasted-JD grounding composes with both mid-session paths:** the reconstructed `_service_brief_from_out` brief round-trips `jd_summary`, so mid-session openings carry it automatically (`generate_opening_question` reads `brief.jd_summary`), and the mid-session `_followup_and_tts(jd_summary=...)` call passes it explicitly — a mid-interview question never mischaracterizes a solo/collaborative role.
  - **No-repeat questions.** Within a session, `_session_opening_avoid_list` feeds every already-asked question (+ the user's cross-session recents) into `generate_opening_question(recent_questions=...)` so a mid-session opening repeats neither an intra-session nor a recent question. Race-safe atomic `UPDATE` in `daily_limit.py`. `GET /me` also runs `check_and_reset` — zero writes steady-state (UPDATE gated by `count_reset_date.is_distinct_from(today)`, NULL-safe). **Second daily limit, same module:** Ask Tutor chats are capped at **10 successful completions/day** (`daily_chat_count` / `chat_count_reset_date`, `check_and_reset_chat` / `enforce_chat_daily_limit` / `record_chat_completion`) — see the Ask Tutor bullet for the success-only-increment nuance. `GET /me` rolls both counters for free tier.

- **Incidents event log (internal/admin-only).** `user_created`, `user_signed_in`, `moderation_request`, `interview_session_started`, `save_question`, `injection_detected`, `job_description_mismatch_ack` (warning — user proceeded past a flagged JD↔profile mismatch; keeps JD + declared company/title for audit), `error`. Written in a fresh DB session (failures never break request). Payload caps: `sent_content` 10k, `error` 8k, large JSON 2k. Auth events backend-observed (no Clerk webhooks); `user_signed_in` dedupes by Clerk `claims.sid`. Moderation incidents log only on OpenAI API fire (not deterministic local rejects). **Moderation fails closed:** `ModerationUnavailableError` writes `error` incident; callers return 503; `ensure_moderation_configured()` aborts boot if `OPENAI_API_KEY` unset. `interview_session_started` logs only after session persistence. 5xx/unhandled errors → `error`; normal 4xx does not. **Every `severity='warning'` insert triggers an ops-alert email** — see the next bullet.

- **Transactional email (Mailgun) — ops alerts + policy-change broadcasts.** `app/services/email.py` is a ~20-line httpx wrapper over Mailgun's `messages` endpoint (mirrors `tts.py`/`company_research.py`, no SDK). `send_email(*, to, subject, text, from_addr=None) -> bool` is **best-effort by contract — NEVER raises**: returns `False` (and logs a warning) when unconfigured or on any HTTP/transport error, so a mail failure can't break incident logging, request handling, or boot. `mailgun_configured()` short-circuits when `MAILGUN_API_KEY`/`MAILGUN_DOMAIN` are unset (no-op in dev/tests). Two callers:
  - **Warning-incident alerts (`incidents.py`).** Hooked generically inside `log_incident` AFTER the successful commit: any `severity == SEVERITY_WARNING` row spawns `_send_warning_incident_email` **fire-and-forget** via `asyncio.create_task` (strong-ref'd in module-level `_email_tasks`, like `_finalize_tasks` in `sessions.py`) so a request-path warning log (e.g. a 422 injection block) isn't delayed by mail I/O. Covers `injection_detected`, `job_description_mismatch_ack`, and moderation hard-blocks with **no per-call-site change** — future warning types are covered automatically. Email → `MAILGUN_INCIDENT_RECIPIENT`, subject `[InterviewPie] Warning incident: {event_type}`, body = type + trigger time + the already-clipped `metadata`/`sent_content`/`returned_content`/`error`. `triggered_at` is captured at the top of `log_incident`. Skipped entirely when Mailgun is unconfigured.
  - **Policy-change broadcast (`policy_notifications.py`).** Policy versions are source constants in `policy_versions.py` (`CURRENT_TERMS_VERSION`, `CURRENT_PRIVACY_VERSION`, `CURRENT_BIOMETRIC_VERSION`); bumping one emails every user with a non-null `email` (any onboarding state — users accept ToS/Privacy before onboarding). `run_policy_notification_sweep_once()` runs **once at startup** (the only moment a deploy could have bumped a version), wired in `main.py` lifespan via `start_policy_notification_sweep()` (gated by `POLICY_NOTIFICATION_ENABLED`, spawned as a background task so a slow batch never delays readiness). Mechanics mirror `delivery_retention_scheduler`: a **distinct Postgres advisory lock** (`0x5D11_3E47_2026_0622`) so one blue/green replica acts, and a **first-run baseline** — a missing `policy_notification_state` row is seeded to the current version **without emailing** (never blast users about a version they already hold). The bumped version is **claimed (state row advanced) under the lock BEFORE any mail goes out** so the peer replica can't double-send; trade-off (accepted) — a crash mid-batch won't re-notify for that policy. Subject `We've Updated Our {display_name}`; terms/privacy bodies carry a re-prompt line (frontend forced-acceptance gate), biometric does not (`/legal/biometric-data-retention` is not in the gate, so no frontend mirror); links use `POLICY_NOTIFICATION_BASE_URL` + per-policy path. Per-recipient send (users never see each other), per-recipient failures tolerated. When Mailgun is unconfigured the sweep still seeds/advances state (so a later config change doesn't backlog a "change" to spam) but skips sends.

## Architecture

```
Browser (React+Vite)
  │── Clerk JWT ──────────────────────► FastAPI
  │── MediaRecorder blob ─────────────► FastAPI
                                          │── ElevenLabs STT (audio → transcript)
                                          │── OpenRouter (DeepSeek v4 Pro evaluator, Gemini research + opening question, DeepSeek v4 Flash follow-up)
                                          │── ElevenLabs TTS (text → audio)
                                          │── Serper API (company research)
                                          └── Postgres (via Alembic)
```

**LLM calls per session via OpenRouter** (five in the default 2-turn flow; more scale with `num_turns`). #1/#2 at session start (research + opening); per non-final turn a **next-question** call (a follow-up, OR a fresh **opening** when the story block pivots — plus a cheap `should_continue_followup` decision call at follow-up-streak 1); #4 evaluates each turn in bg; #5 forward coaching right after #4. Each turn's eval+coaching runs while the user answers the next turn. Final-turn eval+coaching in `_run_background_finalize`, then metrics written + session → `completed`. A longer interview therefore costs proportionally more spend for the same daily-session slot (accepted).

1. **Company research + field classification** (`google/gemini-2.5-flash`). Two parallel Serper queries → `CompanyBrief(description, headlines, values, category, role_signals, sample_question_themes, jd_summary)`. `category` ∈ 15 buckets. **When a job description is pasted, Serper is skipped** and the brief is derived from the posting alone (`_research_from_job_description` + `_JD_SYSTEM_INSTRUCTION`); both paths funnel through `_normalize_brief_payload`. `jd_summary` (role-focused bullets) is emitted **only** on the JD path — see the "Optional pasted job description" MVP bullet. A separate cheap match-check (`openai/gpt-oss-120b:free`, low reasoning, `deepseek/deepseek-v4-flash` no-reasoning fallback, fails open) screens the JD↔profile pairing first — see the "Optional pasted job description" MVP bullet.
2. **Opening question** (`google/gemini-3.5-flash`, minimal reasoning). System by `build_star_opening_prompt(brief.category, rng=None)`; user prompt appends `role_signals`/`sample_question_themes` only when non-empty.
3. **Follow-up question** (non-final turns, `deepseek/deepseek-v4-flash`, no reasoning). Live path is `generate_followup_transition` (JSON `{spoken_bridge, question}`) — the visible `question` is persisted/returned; the `spoken_bridge` is prepended to TTS only. The plain-text `generate_followup` (hard rules 10–25 words + confused-candidate + output-format, output through `_sanitize_followup`) is the fallback/other-caller path. See the "Spoken transition bridge" sub-bullet.
4. **Evaluate** (`deepseek/deepseek-v4-pro`, high reasoning, `deepseek/deepseek-v3.2` fallback, JSON mode, detached bg task). Rubric from `_star_evaluator_rubric.INDUSTRY_GUIDANCE` keyed on `brief.category`.
5. **Forward coaching** (`deepseek/deepseek-v4-flash`, no reasoning, `coaching.py:generate_next_take`, JSON mode). Deliberately SEPARATE call (NOT folded into evaluator's LOCKED prompt). Input: question + transcript + `main_takeaway` + top `improvement_moments`. Writes `feedback_detail.next_take` (`NextTake{focus, approach}`). **Fails soft**: any error → `next_take` null, scoring unaffected.

## Evaluator Schema (LOCKED — do not drift)

- **Models:** Evaluator → `deepseek/deepseek-v4-pro` (high reasoning, `deepseek/deepseek-v3.2` fallback). Research → `google/gemini-2.5-flash`; opening → `google/gemini-3.5-flash` (minimal reasoning); follow-up → `deepseek/deepseek-v4-flash` (no reasoning). No other model mixing.
- **Scores:** five content dims LLM-scored 0–10 ints, then `_calibrate_content_scores` (only lowers); `delivery` computed server-side by `_compute_delivery_score` (never trusted from the model). All six nullable on the wire.
- **Delivery feedback:** built server-side from `cv_summary` (never LLM, not in prompt); omitted when camera declined. `summary` required; four cues optional, each ≤270 chars.
- **Forward coaching:** `feedback_detail.next_take` (`{focus ≤270, approach ≤390}`) NOT from evaluator — written by coaching call (#5) and merged before persistence. Null on legacy turns / coaching failure.
- **Feedback caps:** `positive_moments` ≤ 3, `improvement_moments` ≤ 4, `quick_wins` ≤ 3. Server-side: drop moments whose `transcript_snippet` isn't an exact substring, then `_dedupe_by_snippet` (exact equality, first-occurrence wins) on both lists. **This exact-substring anchoring is now also load-bearing for the frontend** — `QuestionAnswerCard` locates each improvement snippet in the transcript (trimmed `indexOf`) to highlight it inline + make it click-to-jump; relaxing the anchoring silently breaks that highlighting (see `frontend/CLAUDE.md` → "Transcript feedback highlighting").

- Pass full turn history in prompt so follow-ups reference earlier answers. Filler regex is ground truth; LLM breakdown supplemental.

**Filler word regex** (case-insensitive, word boundaries): `um, uh, er, like, you know, basically, literally, actually, i mean, kind of, sort of, right`

**Filler-word RATE (fillers ÷ total words).** `interview_turns.word_count` (NOT NULL DEFAULT 0, `count_words()` whitespace tokenization) and `session_metrics.total_word_count` (nullable). Migration `0011_word_counts` (`down_revision='0010_saved_questions'`); both backfilled from existing `transcript_text`. Rate not stored — derived via `filler_rate_pct(filler, words)` (`Decimal` percent, 1 dp, `None` when no words). Multi-word filler ("you know") = 1 filler but 2 words → rate marginally conservative (accepted). `MeStatsOut.filler_word_rate`: lifetime **word-weighted** Σfillers/Σwords (not mean of per-session rates). **Frontend traffic-light bands** (`fillerRateColor`): ≤5% green, ≤10% yellow, ≤15% orange, >15% red — rendered by `FillerRateBar` (proportional fill capped at 20%).

## Session Rules

- **`num_turns` turns (2–8, default 2)**: `is_final = current_turn.turn_number >= session.num_turns`; `next_question` is empty string on the final turn. Turns form **story blocks** (1 opening + 1–2 follow-ups) — see the "Story-block interviews" MVP bullet for the routing. `num_turns` is frozen at create time on the session row.
- **Early exit is graded, not discarded.** Quitting with ≥ 1 completed turn finalizes the session on those turns via `POST /sessions/{id}/end` — see the "Quit-early grading" sub-bullet. A session can therefore complete with fewer than `num_turns` turns.
